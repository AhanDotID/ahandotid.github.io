GraphQL Thread Metadata Disclosure — Airbnb

📅 2026 ⏱ 5 min read 🎯 HackerOne — Airbnb 👤 Ahan Pahlevi

Overview

While exploring Airbnb's support message system, I discovered that an authenticated user can access partial metadata of another user's support thread by manipulating the globalThreadId parameter in the ViaductGetThreadAndDataQuery GraphQL endpoint. The server returns HTTP 200 with thread metadata belonging to other users, instead of a proper HTTP 403 Forbidden response.

"Being able to know if a user has an active conversation does not appear to pose a security risk." — Airbnb Security Team (Closed as Informative)

Vulnerability Summary

Although message content is properly protected, the endpoint leaks the following metadata when supplied with an unauthorized globalThreadId:

  • Thread ID & existence confirmation
  • Inbox visibility status (hiddenInInbox) — reveals account moderation status
  • Activity timestamps (mostRecentInboxActivityAtMsFromROS)
  • Profile images of support participants

Steps to Reproduce

Step 1 — Setup two Airbnb accounts:

Account A → Attacker
Account B → Victim (test account)

Step 2 — Get victim's thread ID from URL:

Login as Account B, open support chat and note the thread ID from the URL.

Step 3 — Encode the thread ID to Base64:

$ echo -n "MessageThread:[REDACTED]" | base64
[REDACTED_BASE64]

Step 4 — Intercept & modify the request in Burp Suite:

Login as Account A, intercept the ViaductGetThreadAndDataQuery request, replace the globalThreadId value with the encoded victim thread ID, and send via Repeater.

Step 5 — Server returns HTTP 200 instead of 403:

Step 6 — Metadata of Account B leaked in response body:

Proof of Concept

GET /api/v3/ViaductGetThreadAndDataQuery/d8dbf8f7...
  ?operationName=ViaductGetThreadAndDataQuery
  &variables={"globalThreadId":"[REDACTED_BASE64]"...}
Cookie: [Account A session]

--- Response ---
HTTP/2 200 OK
{
  "data": {
    "threadData": {
      "id": "[REDACTED]",
      "hiddenInInbox": true,
      "inboxAccessibilityTemplateText": "You do not have access to this thread.",
      "inboxProfileImages": [...],
      "mostRecentInboxActivityAtMsFromROS": "0",
      "fetchedAt": "[REDACTED]"
    }
  }
}

Impact Analysis

Although message content is protected, the leaked metadata can be used to:

  • Confirm user activity — verify if a target has active support conversations
  • Enumerate moderation status — hiddenInInbox: true indicates account under review
  • Profile activity patterns — support activity timestamps are exposed
  • Attack chaining — valid thread IDs can be enumerated for further exploitation

Remediation

  • Return HTTP 403 for the entire request when user is not authorized — do not return partial data
  • Validate thread ownership server-side before returning ANY field in the response
  • Implement consistent authorization checks across all GraphQL field resolvers

Lessons Learned

Not every finding gets accepted — and that's part of bug bounty. What matters is the process: endpoint enumeration, response behavior analysis, and structured reporting. Metadata disclosure is often underrated, but in the right context it can be a stepping stone for a larger attack chain. Keep hunting.
